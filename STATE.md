## Current Phase: Phase 58 (Transaction defense verdict outranks the bot score)

### Phase 58 Modifications (v2.28.0)

**Problem, from the field.** A named customer of a live WooCommerce store could not complete an order on 2026-08-26 and emailed the store to ask whether he should "call a human or try the incognito approach". The operator found nothing: WP Activity Log had no record, the Transaction defense list in Cloud Console showed 8 successful transactions and no risky ones, Stripe had no block, and blocking on high-risk transactions was switched off. The single assessment behind the refusal (Cloud Logging, 14:25:26.191Z) read:

```
riskAnalysis.score                        0.2
riskAnalysis.reasons                      ["UNEXPECTED_ENVIRONMENT"]
tokenProperties.valid                     true
tokenProperties.createTime                14:14:49.758Z   (10m36s before use)
tokenProperties.action                    "checkout"
fraudPreventionAssessment.transactionRisk 0.10000000149011612
event.userIpAddress                       159.100.171.53  (VPN exit, Atlanta)
```

**Nothing was wrong with the token.** It was `valid: true` and carried the right action. The refusal was the score gate in `verify_token()`: 0.2 against the 0.5 default for `gswp_threshold_checkout`, which returned `recaptcha_low_score` and told the customer his order was "rejected as potential spam". He was on a VPN, on a phone, returning to a checkout tab he had left for ten minutes to fetch his wallet from the car — which is what a 0.2 with `UNEXPECTED_ENVIRONMENT` actually describes.

**The plugin had a second, better answer in hand and ignored it.** The same assessment carried `transactionRisk: 0.10` — Google's payment fraud model, looking at the same event *with the transaction attached*, called it safe. `validate_checkout()` reads the score first, adds the error, and only then calls `process_fraud_prevention()`, so the fraud verdict never got to speak. **Two independent judgements, and the weaker one about the browser was overriding the stronger one about the payment.**

**A VPN is not evidence about a card.** This was never going to be a one-off: a corporate VPN, a privacy extension, a mobile carrier proxy or a locked phone depresses the score of every legitimate shopper behind it, and each one would have been refused and accused.

**Decision:** where a fraud verdict exists and is below the blocking threshold, it decides. `GSWP_Verifier::fraud_verdict_admits_low_score()` is consulted before the low-score `WP_Error` is built, and admits the submission when `transactionRisk < gswp_threshold_txn` (default 0.8). Deliberately keyed on the threshold rather than on `gswp_txn_block`: the threshold defines what counts as risky, the toggle only decides whether risk alone blocks.

**Carding does not benefit.** Automated card testing scores low AND returns high `transactionRisk` — the case Transaction defense exists to catch — so it fails the check and is refused on the score exactly as before. The override only ever admits a transaction Google's fraud model has already cleared. The comparison is `>=` refuses, matching `process_fraud_prevention()` so the two cannot reach opposite conclusions about one payment.

**Reachable only where transactionData was sent:** WooCommerce classic checkout, the Store API block checkout, and Gravity Forms / Fluent Forms payment forms. Login, registration, comments and non-payment forms leave `$last_fraud_assessment` null and are untouched.

**The message.** "Verification score too low. Submission rejected as potential spam." is gone from all three files that carried it. This is the second incident in this project's history where that sentence was shown to a working customer — Phase 48 was the first, a named customer told she was spam while editing her own profile. The docblock on `log_rejection()` already says a rejection nobody can explain is a defect in its own right; a rejection that *misexplains* itself to the customer is the same defect with a worse blast radius. The operator-facing log still records the exact score and threshold, so nothing is lost for diagnosis.

**Changes:**

- `includes/class-gswp-verifier.php`:
  - Added `fraud_verdict_admits_low_score()` (public, so the two form providers can consult the same decision), with the `gswp_defer_score_to_fraud_verdict` filter as the escape hatch back to pre-2.28.0 behaviour. Logs whenever it admits — a submission that would have been blocked and was not is exactly the event an operator needs to find afterwards.
  - The low-score branch of `verify_token()` consults it first and caches `true` under the existing token-cache key on admission, so a second verification of the same token in one request agrees with the first.
  - Reworded the `recaptcha_low_score` message. The error **code** is unchanged, so anything keying on it keeps working.
- `includes/class-gswp-provider-gravity-forms.php`, `includes/class-gswp-provider-fluent-forms.php`: the action-mismatch fallback re-applies the score threshold itself, bypassing the verifier's own gate, so both now consult `fraud_verdict_admits_low_score()` too. Same reworded message.
- `tests/manual/30-checkout-score-vs-risk.php`: new. Replays the incident's actual assessment values, asserts carding is still refused, checks the threshold boundary, checks the four no-transactionData contexts, and greps the plugin for the accusatory string.

**Evidence, stated plainly:** `php -l` on all four touched files, and an 11-assertion stub harness (WordPress functions faked, private state seeded by reflection) covering the incident replay, the carding case, both sides of the threshold boundary, the null-verdict contexts, a missing `transactionRisk` key, an operator-lowered threshold, and the filter in both directions. **No WordPress, no WooCommerce, no browser, no live site.** `tests/manual/30` has not been run. Per the Phase 57 lesson, note what that evidence does *not* cover: the harness proves the decision function, not that `validate_checkout()` and `validate_store_checkout()` reach it on a real request. The staging check that settles it is a real checkout that scores below threshold with a low fraud risk.

### Phase 58 completion (v2.29.0)

The two items v2.28.0 deferred, both now done. They are independent of each other and of the 2.28.0 change; each is separately revertable.

**1. Client IP resolution (`includes/class-gswp-client-ip.php`, new).**

`GSWP_Client_IP::get()` replaces the six raw `REMOTE_ADDR` reads (the verifier, the alert layer, four in the REST API). There is now no raw `$_SERVER['REMOTE_ADDR']` anywhere in `includes/` outside that one class.

**The reason this took a class rather than a line** is that the obvious fix is a security hole. Any client can send `X-Forwarded-For`. A plugin that reads it unconditionally hands an attacker a way to launder a bad score: submit from a flagged address, claim a clean residential one, and the assessment is created against the claim. `REMOTE_ADDR` is the only value in a request an attacker cannot choose, which is why it was the safe default and why the fix could not be to stop using it.

So: the header is read **only** when `REMOTE_ADDR` is itself a proxy the operator has declared, and the chain is walked from the **right** — the end nearest this server, which each hop appends to — skipping trusted hops until an address appears that no trusted hop vouched for. Everything further left was written by something we do not trust and is never examined. A malformed entry at the trusted end aborts the walk rather than skipping past it; skipping would step over the boundary between what the chain can attest to and what it cannot.

Default is an empty trusted list, so **upgrade changes nothing** until proxies are configured — `gswp_trusted_proxies` (option or filter, addresses and CIDR ranges, IPv4 and IPv6) and `gswp_client_ip_header` (X-Forwarded-For, CF-Connecting-IP, True-Client-IP, X-Real-IP). Both are validated on save; an entry that is not an address or range is dropped at the door, because a typo here fails silently — it simply never matches, and the site goes on reporting its CDN's address forever.

**A site that is misconfigured now says so.** When a request carries a forwarding header and no proxies are trusted, the plugin logs a warning, once per twelve hours, naming the address it is about to send Google. Deliberately hedged and throttled: the header's presence is a hint, not proof, since a passing scanner can send one at a direct-served site. But the symptom of getting this wrong — every visitor scoring low, for no visible reason — otherwise gives an operator nothing at all to search for, which is how the 2026-08-26 incident consumed a morning.

**This operator's own site does not need it.** The origin already restores real client IPs behind QUIC.cloud; the admin's diagnostic assessment carried their real address, which is what ruled the CDN out as a cause of Dave's 0.2 and left the VPN as the explanation. The class exists for the customer sites where that is not true.

**2. Token freshness at checkout (`get_bootstrap_js()`, `assets/js/gswp-blocks-checkout.js`).**

`fetchToken()` now stamps `data-gswp-minted` when a token resolves, and the `checkout_place_order` veto treats a token older than the refresh interval (100s, against a 120s lifetime) as it already treated a missing one: mint a fresh one, then resubmit. A field older than the interval is one the interval did not reach — a hidden tab or a locked phone, where the browser suspends timers. That is the ten-minute-old token from the incident.

**The INVARIANT holds.** Staleness is read, never written: the old token stays in the field until a new one resolves, and if none can be minted the stale one is still submitted. Stale is a reason to try for a better token, never a reason to block a payment.

**Veto suppression is keyed to failure, not to elapsed time, and the first draft got this wrong.** A flat "one veto per 5 seconds" cooldown stops the spin (fetch fails, resubmit, veto, fetch fails…) but it also throttles the *empty*-field veto, which previously always fired — and the `checkout_error` path blanks the field deliberately, so a customer clicking again within the cooldown would have submitted an empty token. The DOM stub caught it. Vetoes are now free while tokens can be minted and stop for 15 seconds only once minting has actually failed.

The block checkout had no `visibilitychange` refresh at all — the classic bootstrap has had one since 2.22.1 — so the same stale submission was possible there. It now refreshes on visibility and on bfcache restore. The residual race remains: the Store API request is assembled from extension data at submit time and the rising-edge refresh cannot block it, so a fresh token is best-effort there rather than guaranteed. Closing that needs a Blocks validation hook and is not attempted here.

**Evidence, stated plainly:** `php -l` on every touched PHP file; `node --check` on both the extracted inline bootstrap and the block checkout script; a 35-assertion PHP stub harness for the IP resolver (both spoofing shapes, multi-hop chains, IPv4 and IPv6 CIDR including /0 and byte-boundary cases, malformed chains at each end, single-value headers, both filters); and a 25-assertion DOM stub for the bootstrap (mint stamping, fresh token not vetoed, the incident's stale token vetoed and replaced, the never-empty invariant across both, repeated vetoes while minting works, suppression only after a mint failure, and the empty-field path). `tests/manual/31-client-ip-and-token-freshness.php` is new and **has not been run**.

**No WordPress, no WooCommerce, no browser, no live site.** What the stubs do not cover: that `GSWP_Client_IP::get()` is reached on a real assessment (the wiring is a six-site substitution, verified by grep, not by execution), and that WooCommerce's real `checkout_place_order` event sequences with the veto as the jQuery stub does. The staging checks that settle these are one checkout from behind a configured proxy with the assessment's `userIpAddress` compared against the order's customer IP, and one checkout left idle for three minutes before Place order is pressed.

**Superseded note, kept for the record.** v2.28.0 recorded these two items as deliberately not done, with the reasoning for deferring them. That reasoning was: fixing the IP means trusted-proxy configuration and is not worth guessing at, and the freshness guard is a separate risk surface constrained by the INVARIANT. Both still hold — this entry is what acting on them looks like, not a reversal.

### Phase 58 deferrals as recorded at v2.28.0 (both now closed above)

1. **`get_remote_ip()` still returns `REMOTE_ADDR` and nothing else** (six call sites: the verifier, the alerts class, four in the REST API). On this operator's site that is correct — the origin already restores real client IPs behind QUIC.cloud, confirmed by the admin's own diagnostic assessment carrying their real address. On a site behind a proxy that does *not* restore it, every assessment would carry the CDN's IP: scores depressed for everyone, Account Defender learning against one shared address, and alert emails naming the wrong IP. Fixing it means trusted-proxy configuration, because blindly trusting `X-Forwarded-For` would let anyone launder a bad score by forging a clean address in a header — which is why the code reads `REMOTE_ADDR` in the first place. Worth doing, not worth guessing at.
2. **Nothing holds a submission for a fresh token.** The 10m36s-old token in the incident was submitted because the refresh loop is skipped while `document.hidden` and the `visibilitychange` refresh is fire-and-forget; the `checkout_place_order` veto only catches an *empty* field, never a stale one. A freshness guard (stamp the mint time, treat an over-age token as empty) would have minted a new token for that submission, which would have scored better than a ten-minute-old one even from a VPN. Separate change, separate risk surface — the INVARIANT note in `get_bootstrap_js()` constrains it, since a token field must never be observably empty.

## Historical Phase: Phase 57 (Admin password resets exempt from token enforcement)

### Phase 57 Modifications (v2.27.3)

Reverses the approach taken by Phases 54–56. Full investigation, with core source citations and the alternative that was considered and rejected, is in `PLAN-admin-password-reset.md`.

**Problem:** two errors reported from the live site on v2.27.2, both with `gswp_enable_wp_lostpassword = 1`:

- `user-edit.php` / `profile.php` → **Send Reset Link** → *"Error: Anti-spam verification token is missing."*
- `users.php` → **Send password reset** (row link and bulk action) → *"Password reset links sent to 0 users."*

**Four defects, all in this plugin.** Verified against WordPress core on the 6.4, 6.7, 6.8 and 6.9 branches — the three core behaviours involved are byte-identical in all four, so **this was never a core regression**. It arrived with v2.26.2, which began enforcing on screens that had never carried a token before.

1. **The row-action guard has never matched.** `validate_lostpassword()` tested `isset( $_GET['user'] )`; core builds the link as `users.php?action=resetpassword&users=$id` (`class-wp-users-list-table.php:507`). The parameter is `users`. The guard returned false on every request it existed to catch.
2. **The Users bulk form is a GET form.** `users.php:806` renders `<form method="get">`, and `restrict_manage_users` fires inside it. The injected field therefore arrived in `$_GET`, while `GSWP_Verifier::verify_token()` reads only `$_POST`. The bulk path could never see a token — which also means the request-scoped token cache added in v2.27.2 *specifically* for bulk reset was never reachable: the request failed at the empty-token check before any API call.
3. **The admin inline script matched the wrong action name.** It gated on `body.indexOf('action=send_password_reset')`. `user-profile.js:131` sends `wp.ajax.post( 'send-password-reset', data )`; `admin-ajax.php:144` lists the hyphenated form in `$core_actions_post` and line 166 derives the handler name with `str_replace( '-', '_' )`. The underscore form is the PHP function name and never appears in a body, so the interception never fired and the request left with no token.
4. **The post-failure refresh patch was dead code.** It overrode `XMLHttpRequest.prototype.addEventListener`, but jQuery 3.7.1 assigns handlers as properties (`xhr.onload = callback()`, `jquery/src/ajax/xhr.js:118`) and never calls `addEventListener`. It also replaced the prototype method for every XHR in wp-admin, adding a `JSON.parse` of every POST response for no benefit.

**Decision:** exempt admin-initiated resets rather than keep chasing delivery. All three entry points are performed by an authenticated administrator and are already gated on a capability check and a WordPress nonce, both verified by core before `retrieve_password()` is reached. reCAPTCHA v3 scores anonymous browser traffic; against an admin inside wp-admin it adds nothing those controls do not already provide, and every attempt to attach it has instead hard-blocked a legitimate action. The one path that *could* technically carry a POST token (the profile AJAX button) was exempted too rather than fixed with a one-character change, because keeping it meant keeping ~160 lines of `XMLHttpRequest.prototype` patching in wp-admin for no security gain.

**This is not the request-body opt-out the A4 note in `GSWP_Verifier::verify_token()` warns about.** Each branch of the predicate re-proves the capability and the nonce for itself, so a caller cannot reach the exemption by omitting or forging a field — it must already hold the privileges that make the reset legitimate. The public lost-password form satisfies neither branch.

**Four details here were wrong in the first cut of this phase and are worth keeping written down, because two of them were silent breakages rather than visible ones.**

**`comment_form_defaults` is not a safe injection point.** Core merges the theme's own `comment_form()` arguments *over* the filtered defaults — `$args = wp_parse_args( $args, apply_filters( 'comment_form_defaults', $defaults ) )` — so any theme that customises `submit_field` drops the token field while server-side enforcement stays on, rejecting every comment from every non-privileged visitor with "verification token is missing". This is exactly the divergence the A4 note in `GSWP_Verifier::verify_token()` exists to prevent: **the render gate and the enforcement gate must agree, and a third party must not be able to break the agreement.** The `comment_form` action cannot be suppressed by a theme argument.

**`pre_comment_approved` is not comment-form-only.** `WP_REST_Comments_Controller::create_item()` calls `wp_allow_comment()` directly, which reaches the same filter via `wp_check_comment_data()`. A REST request carries no `g-recaptcha-response`, so enforcing there returned `recaptcha_missing` for every REST comment — and the controller returns that `WP_Error` unstatused, which the REST server renders as **HTTP 500**. `is_admin()` is false for REST, so `GSWP_Comments` is instantiated on those requests. Because `moderate_comments` users are exempt, an operator testing as an administrator would never see it: the break lands on subscribers and anonymous commenters via mobile apps, headless front ends, and AJAX comment themes. The fix gates on `pre_comment_on_post`, which fires only inside `wp_handle_comment_submission()` — the wp-comments-post.php handler. XML-RPC pingbacks and programmatic `wp_new_comment()` calls skip it too, which is correct: none of those paths can carry a token. This is not a bypass seam, since a caller cannot reach `wp_handle_comment_submission()` while avoiding the action, and core disallows anonymous REST comment creation by default.

**The shared bootstrap does not hold a comment submit.** Its preventDefault-and-hold is scoped to `form.login, form.register` and is deliberately not widened (see the INVARIANT note in `GSWP_Recaptcha_Loader`), so a page-cached post served while the reCAPTCHA script is still loading could post an empty field and hard-reject a legitimate comment. The scoped snippet covers that window without touching the 2.22.1 bootstrap, which is still the largest unproven surface on `main`. One trap in it: the core comment form's submit button is `<input name="submit">`, which shadows `form.submit` on the element, so the snippet holds a reference to `HTMLFormElement.prototype.submit` and calls it against the form.

**`validate_lostpassword()` must return after a failed score.** The first cut continued into Account Defender screening after a reCAPTCHA refusal, stacking a second error message on the same form for the same request. The score already prevented the reset email from being sent, so the screening added noise without effect. The fix returns immediately on a `WP_Error` from `verify_token()`, matching `validate_register()` which already does this.

## Historical Phase: Phase 50 (Fluent Forms provider — parity with Gravity Forms)

### Phase 50 addendum (v2.23.1) — first live-install results

Chunks 20–26 were run on `test.onedog.solutions` (Fluent Forms **6.2.9**, Pro 6.2.7, PHP 8.3, Enterprise keys). The suite did its job: it found a defect in the provider that no amount of `php -l` would have, and it found it before the provider had been switched on anywhere.

**The defect: `raw_option()` was blind to object-typed settings.** Chunk 23 crashed with *"Object of class stdClass could not be converted to string"* on `__fluentform_payment_module_settings`. The crash was in the test chunk, but the cause was a fact about Fluent Forms nobody had established: **it stores some options as a serialized OBJECT, not an array.** `raw_option()` handled the array case and the JSON-string case, and returned `null` for everything else. So an object-typed option read as *absent*.

If the reCAPTCHA configuration is one of those, `native_captcha_state()` would have returned `unknown` for a captcha that was configured and running, `form_is_eligible()` would have returned true, and this plugin would have taken over a form still carrying a live Fluent Forms captcha.

That is **Phases 43/44 word for word**: detection reporting "not configured" for a host plugin that was configured, because we looked in a shape it does not use. ### Phase 50 Modifications (v2.23.0)

`GSWP_Provider_Fluent_Forms`, implementing the same `GSWP_Form_Provider` contract as the Gravity Forms provider, reaching the 2.22.0 feature surface: enumeration, injection, coverage recording, scoring, classification (payment / creates account / updates account / changes password), per-class thresholds, asymmetric enforcement, the coverage assertion, the "Not public" declaration, per-form rejection reasons, native-captcha detection, Transaction Defense and submission meta.

**The architecture held.** The registry, kill switch, `audit()`, the `method_exists()`-guarded diagnostics, `GSWP_Recaptcha_Loader` and `GSWP_Verifier` all took a second provider unchanged. `PLAN-form-provider-replacement.md` §7.4 said a provider needing interface changes would mean stage 1 over-fitted to Gravity Forms. It needed exactly one, and it is not an over-fit — it is a case the original enum could not express at all.

**The interface finding: `native_captcha_state()` assumed the host's captcha is Google's.** It returned `off` / `v3` / `v2` / `unknown`. Fluent Forms ships reCAPTCHA, hCaptcha **and** Turnstile, configured identically, and every available answer for the latter two is wrong in a different way: `off` is a lie, `v2` misnames the product to an operator who then hunts for reCAPTCHA settings that do not exist on their site, and `unknown` leaves the form *eligible* — so we would take over a form already running Turnstile. Widened with `other`. It sits in the eligibility path rather than behind a `method_exists()` guard, unlike `form_policy()` and `last_rejection()`, because that guard pattern is right for diagnostics a provider may not have, and this decides whether we cover a form at all. Eligibility logic must not be optional.

**Three places Fluent Forms is genuinely not Gravity Forms**, and they are where the work went:

1. **The submission is AJAX, so the token is probably not in `$_POST`.** Fluent Forms serialises the form into a single request parameter. A direct port of `validate_submission()` would have read an empty token on every submission of every form — and on a payment or account form that fails **closed**, permanently, for every visitor. That is the Phase 48 defect again, with the same delivery vector. `submitted_token()` tries three transports (parsed `$formData`, the serialised envelope, plain `$_POST`) and is correct under any of them. The 2.17.0 rule is untouched: reading the *token* from the request is fine, it is request data; the *enforcement decision* still comes from the stored form definition.

2. **A rejection may not be visible.** Fluent Forms attaches validation errors to fields; our token field is not one of its registered fields, so an error keyed to it may be delivered and then dropped for want of a DOM node — the visitor watches the button spin and stop. Phase 48 already burned a debugging cycle on that exact symptom (it turned out to be GF refusing on hidden required fields) and recorded the rule: **this plugin has no branch that hangs a submission.** `error_field_for()` resolves a real field to carry the message, and when it cannot, `reject()` **admits the submission and logs loudly instead of rejecting it**. A rejection nobody can see is indistinguishable from an outage.

3. **There is no whole-markup filter.** `inject_into_markup()` is not decoration on the GF provider — with the staged rollout gone it is what makes coverage independent of having guessed the render paths right. Fluent Forms has no `gform_get_form_filter` equivalent, so the backstop is an output buffer opened on `before_form_render` and closed on `after_form_render`. Buffering a third-party render is invasive and can be left unbalanced by a fatal, so it is gated twice: it only opens for a form the primary hook has never succeeded on, and it refuses to close a buffer whose nesting level does not match what it opened, reporting a coverage gap instead.

**Classification is easier here in one place and harder in another.** `fluentform_forms.has_payment` is a direct authoritative column where GF sniffs eight add-on slugs — but the field-type fallback is kept anyway, and an unparseable form definition still classifies as payment. Account create-vs-update is the mirror of GF's unverified `meta['feedType']`: feeds live in `fluentform_form_meta`, the `meta_key` is unconfirmed, it fails to `create`, and `gswp_ff_account_feed_type` lets a site correct it without waiting for a release.

**Payment blocking is off by default and that is not caution, it is the 2.16.0 question.** If Fluent Forms authorises the card in the browser before the submission reaches us, a server-side rejection stops the order and leaves a hold standing on a real customer's card. Unanswered, so `may_block_payment()` returns false and the provider scores, logs and annotates but does not block. `gswp_ff_txn_block_allowed` turns it on per site once chunk 25 has been run against the gateway dashboard. The settings screen says this in plain language rather than silently doing less than the operator expects.

**The provider ships OFF, and `maybe_migrate()` was changed to make that possible.** It previously enabled any active provider with no stored preference. That is what delivered the Phase 48 defect to sites that never opted into form replacement, for a provider whose bindings had already been wrong four times (Phases 43, 44, 45 twice, 47). These bindings are *less* verified than those were at 2.20.0 — the vendor documentation site was unreachable from the authoring environment, so they were assembled from search excerpts plus the one option name this project confirmed during the Smart Key Scavenger work. `migrates_by_default()` holds a list rather than testing an id inline, so flipping it is a one-line change in the release that has field reports to justify it.

**Discovery is a deliverable, not a prerequisite that was skipped.** `tests/manual/20-26` settle the bindings on the operator's install: detection surface, render coverage and hook balance, submission shape and rejection visibility, captcha options, classification evidence, payment lifecycle, and offline regression guards. Chunk 26 asserts action pairing the way chunk 19 does for Gravity Forms — one resolver, two callers, compared by rendering the real field. That defect is not re-learnable cheaply.

**Also fixed while here:** the `Changes a password` threshold has existed as an option since 2.22.0 but was never rendered, so the class of form most worth tuning could only be reached through the database. Both providers now show the dial. And the "Not public" list and the threshold dials are keyed per provider — a single shared list would have had Gravity Form #3 silencing the alarm on Fluent Form #3.

**Not done, and stated as such:** chunks 20–26 have not been run. Nothing in this phase was verified against a live Fluent Forms install.


## Historical Phase: Phase 49 (a spent token is not a spam signal)

### Phase 49 Modifications (v2.22.1)

Arrived as a support ticket: a client's user was told *"the spam something has expired"* on a PowerPack login form, twice, then it worked on its own while she was on the phone. Attributed by the operator to the "Require 2FA on suspicious logins" toggle.

**The step-up was not the cause and is not defective.** `gswp_ad_step_up` sets a request flag (`class-gswp-account-defender.php:220`) read in exactly one place: the trusted-browser bypass at `class-gswp-two-factor.php:481`. `enforce_second_factor()` returns early for anyone without an enrolled second factor (`:463`), so on a site with no enrolled users the toggle is a **no-op** — it cannot prompt, block, or delay a login. The admin copy already says so accurately (`AccountDefender.jsx:117`). No change made. Recorded because "the security feature we just enabled broke a login" is the natural hypothesis and it was wrong; the enrolment gate is what makes it wrong, and that gate is easy to miss when reading the step-up in isolation.

**Actual root cause: nothing was tied to a submission, and a submission is the only thing that spends a token.** v3 tokens are single use. The footer bootstrap refreshed on load, on a 100-second interval, on tab refocus, on DOM insertion, and on a WooCommerce checkout notice — five triggers, none of them a submit. A form that stays in the DOM (any AJAX login form; a Gravity Form between pages) therefore resubmitted the spent token, Google returned `DUPE`, and the visitor got "Anti-spam verification expired" regardless of what they typed. **The recovery was the 100-second interval**, which is exactly why the form appeared to heal itself with no explanation and why a password reset would not have helped.

The first failure can be anything — a mistyped password, a held 2FA login, a declined card. Whatever it is, PowerPack validates the token *before* `wp_signon()` (`class-gswp-powerpack.php:247`), so attempt 1 spends it and **attempts 2..n inside the window fail for a reason unrelated to the visitor.** `wp-login.php` never had the bug: its own inline script re-mints on every submit (`class-gswp-login.php:445-464`). The Blocks checkout script did not either — it refreshes on the processing-state edges, with a comment saying single-use tokens need a fresh one for retries (Phase 44 notes). The shared bootstrap is the one place that never got the equivalent.

**The fix is shaped by Gravity Forms, not by the login form.** The GF token field carries the same `.g-recaptcha-response` class (`class-gswp-provider-gravity-forms.php:998`), so the same bootstrap fills it, and a GF form that takes payment or creates an account is *strict* and **fails closed on a missing token** (`:1080-1088`). The obvious implementation — blank the field, then refetch — opens a several-hundred-millisecond window in which a customer clicking Pay has a live Stripe transaction rejected outright. **That is worse than the bug being fixed.**

So: **tokens are replaced in place and never cleared.** `fetchToken()` assigns only when the new value resolves, so a field that has ever been populated is never observably empty. The degraded case is a stale token and a soft "please try again" — never a hard block. This is now written as an INVARIANT in the `get_bootstrap_js()` docblock, because it is not inferable from the code it constrains and the next edit will not otherwise know it exists. The single deliberate exception, `clearCheckoutTokens()`, is scoped to `form.woocommerce-checkout` and paired with an immediate refresh.

**Changes, all inside `get_bootstrap_js()`** (inline JS printed from PHP — no `src/`, no build step, no PHP behaviour, no options, no REST):
- `replaceToken()` / `replaceAfterSubmit()` / `tokenFieldIn()` helpers.
- The `submit` listener now does two separable jobs. The legacy `preventDefault()`-and-resubmit fallback stays scoped to `form.login, form.register` — intercepting an arbitrary form is not something to widen casually, least of all a payment form. The post-submit replacement is universal.
- A `click` backstop for modules that submit from a click handler calling `preventDefault()`, so no `submit` event ever fires. **Deliberately not a global jQuery `ajaxComplete` hook**, which was the first draft: a GF page fires AJAX for multi-page navigation, conditional logic, and the Stripe add-on's payment-intent calls, and re-minting against a form that is mid-payment on every completed XHR is not a trade worth making.
- `pageshow` + `persisted` for bfcache restores: timers are paused while frozen, and `visibilitychange` does not fire for a page that was already visible.

**Secondary path this also covers:** `validate_submission()` has no multi-page guard, and `gform_validation` fires per page transition, so each "Next" on a multi-page GF form spends the token. Today the AJAX re-render happens to supply a fresh field, but only after a 250 ms debounce plus a network round trip — an impatient click beats it. The click backstop closes that without touching server-side validation semantics.

**Verification.** `php -l` clean. The generated JS was extracted, `node --check`ed, and exercised against a hand-rolled DOM stub (12 assertions, all passing) covering: an AJAX login form is not intercepted and its token survives submit intact then gets replaced; the field is **never** blank mid-flight, including on a payment-shaped form; the legacy empty-token login fallback still holds the form and resubmits; a click outside any form is harmless; bfcache mints a new token. **This is a stub, not a browser** — it proves the control flow and the never-empty invariant, not real `grecaptcha` behaviour or how PowerPack/GF/Stripe actually mutate the DOM. Live staging is still required and is listed in `PLAN-suspicious-login-2fa-and-stale-token.md`.

**Unverified, and deliberately left so.** Whether a Stripe decline re-renders the GF form (empty-field window → `missing token`) or reports client-side without a re-render (spent token → `recaptcha_expired`) needs the add-on's source or a live decline. Both are plausible, both are real, and the fix addresses both, so it was not worth guessing at. The distinction is diagnostic, not behavioural.

**Operator-visible diagnostics, and a gap.** GF rejections land per form in `gswp_gf_last_rejection` and are already surfaced on the Form Protection tab (`FormProtection.jsx:468`) — check the Stripe forms for `recaptcha_expired` or `missing token`, remembering the 5-minute same-reason throttle (`:1229`). The verifier's own rejection log has no such surface: `GSWP_Log::tail()` (`class-gswp-log.php:133`) **has no caller anywhere** — not REST, not `Diagnostics.jsx`. On a WooCommerce site that is masked by the WC log viewer; this site has no WooCommerce, so the plugin's record of what it rejected is reachable only by WP-CLI or a DB read. That is why this ticket needed a code read rather than a log check. **Surfacing the tail on the Diagnostics tab is the obvious next phase.**

## Historical Phase: Phase 48 (a real customer accused of being spam)

### Phase 48 Modifications (v2.22.0)
A named, known-good customer was blocked from the account dashboard's "User Profile" Gravity Form and told: *"Verification failed. You have been flagged as potential spam."* The client had spoken to her. She was not spam, and the plugin was not saying she was — it was showing a spam accusation for a condition that had nothing to do with her.

**The message was a lie the code told about itself.** A genuine low score produces a *different* string ("Verification score too low"). The one she saw is reachable only when the token is rejected or its action label mismatches. Google never judged her traffic at all.

**Root cause: the action was decided twice.** `token_field()` labelled the token `form_has_payment() ? 'checkout' : 'submit'`. `validate_submission()` expected `$payment ? 'checkout' : ( form_creates_account() ? 'register' : 'submit' )`. For a non-payment form with a User Registration feed those disagree — rendered `submit`, expected `register` — and Enterprise assessments reject on `expectedAction` mismatch before scoring. **Every submission of every account form failed, for every visitor, deterministically.** She was simply the one who reported it.

This is a new instance of an old failure mode in this file: not an inferred *binding* (Phases 43–45, 47) but an inferred *invariant* — that two independently written expressions would stay in agreement. Every other integration here (`class-gswp-login.php`, `class-gswp-powerpack.php`, `class-gswp-xootix.php`) pairs render and validation correctly; the GF provider is the only one where the two were written separately, and the only one that drifted.

**Delivery vector:** `maybe_migrate()` turns the GF provider on automatically at upgrade for any site with GF active and a site key. A site that never opted into form replacement acquired this defect silently at 2.20.0.

**Fix — one resolver, two callers.** `action_for()` is now the single source for both the rendered `data-recaptcha-action` and the expected action. The two ternaries are gone. Correcting one of them would have left the invariant intact and unenforced; removing the duplication is the fix. `accepted_actions()` additionally tolerates `submit` on non-payment forms so pages cached under 2.21.1 do not keep rejecting customers until every cache expires — not a bypass, since both names are ours, the token must still be valid for our own site key, and the score still applies. **Remove in 2.23.0.**

**Fix — rejections stopped accusing visitors.** `recaptcha_failed` now covers only genuinely unexplained failures. Expired/reused tokens, `BROWSER_ERROR`, and `SITE_MISMATCH` each say what actually happened. The classic path gained the `timeout-or-duplicate` branch it never had — the single most common siteverify failure was reported as spam, which on a phone (where the report came from) is routine and blameless. The only surviving spam accusation is the low-score one, which is honest.

**`SITE_MISMATCH` deliberately does NOT fail open**, unlike the bad-secret path directly above it. The precedent does not transfer: our stored secret is not attacker-controllable, but a token is — anyone with their own reCAPTCHA account could mint one against their own key and walk past verification. Logged loudly, still blocked.

**Fix — rejections are now logged at all.** Every rejection path wrote nothing anywhere: no error codes, no `invalidReason`, no observed action. Five materially different causes were indistinguishable, which is precisely why this arrived as "is this person a spammer?" instead of "form #N rejects on action mismatch". `log_rejection()` records context, expected vs actual action, Google's reason, and score vs threshold. **A rejection nobody can explain is a defect in its own right.**

**Changed — a profile edit is not a signup.** `account_feed_type()` splits User Registration feeds into `create` and `update`. Update feeds are scored but non-strict: WordPress has already authenticated the person editing her own profile, and locking her out of her own account details is worse than admitting one unscored edit. Create feeds are unchanged and still fail closed. *UNVERIFIED binding:* `meta['feedType']`. Guarded — an unreadable feed type is treated as `create`, identical to pre-2.22.0 behaviour — and chunk 19 prints the raw value per form to settle it.

**Changed — GF forms stopped borrowing the WP registration threshold.** Every non-payment GF form was scored against `gswp_threshold_wp_register`. A site that raised that to fight fake signups was silently applying signup strictness to its contact forms. New contexts: `gf_submit`, `gf_register`, `gf_account_update`, all defaulting to 0.5.

**Added — per-form diagnostics** (`form_policy()`, `last_rejection()`) surfaced in the coverage table via `method_exists()` guards rather than widening the provider interface, so a second provider is not forced to implement diagnostics it has no equivalent for.

**Fixed on operator review — the Sensitive column could not tell the truth.** The audit row computed `'account' => $strict && ! $payment`, making the two mutually exclusive *by construction*: a form that both takes payment and creates an account reported only "payment", hiding the more security-relevant of the two facts behind the less. The client's Registration form is exactly that — it takes payment and conditionally creates a user when the submitter is not logged in. The column now composes all applicable labels ("payment + creates account") and reads account state from `account_feed`, which is independent of payment. A reporting surface that cannot express a conjunction is not a reporting surface.

**Added — `gswp_gf_account_feed_type` filter.** The feed-type binding is unverified and misreading it is not cosmetic: a profile-edit form mistaken for a signup is scored under the stricter threshold and rejected outright on a missing token. A site that hits this can now correct it per form without waiting for a release. Every return path in `account_feed_type()` routes through it, including the `create` fallback — which is the one an affected site would actually need to override, and which an earlier draft of this change bypassed.

**Fixed on operator review — the plugin assumed every form has a visitor.** The Certificate form is never rendered publicly; the site submits it programmatically when a student completes a course. Nothing in this codebase modelled that, and every consequence pointed the wrong way: the coverage table showed a permanent "no token seen yet" with the un-actionable instruction to *load it on the front end*, and each certificate generation logged a COVERAGE GAP **at error level** and fired `gswp_form_coverage_gap`, emailing the operator. Reproduced in the harness before fixing: without the declaration the alert fires on every run; with it, the form is skipped entirely.

An alerting channel that cries wolf on routine activity is worse than no alerting, because it trains the operator to ignore the one that matters — and this plugin's whole coverage-gap design rests on that alert being believed.

**Fix — `INTERNAL_OPTION` / `form_is_internal()` / `gswp_gf_form_is_internal`**, surfaced as a "Not public" checkbox per form. An internal form is ineligible, so injection, validation, coverage reporting and alerting all skip it through paths that already existed. Deliberately an **operator declaration**, never inferred from the request: deriving it from request shape would let a caller opt out by omitting a field, which is the bypass class removed in 2.17.0. The table now distinguishes "not scored" (declared internal) from "not eligible" (v2 challenge we decline to replace) — reporting both as the latter would send the operator chasing the wrong thing.

**Fixed on operator review — an upgrade overruled the operator.** `maybe_migrate()` stores GSWP_VERSION in MIGRATED_OPTION, so it re-runs on **every** version bump, and its only skip condition was "already on". A provider explicitly switched **off** read as merely not-yet-on and was switched back on. Any operator who disabled form protection — including on our own advice as the mitigation for this very defect — would have had it silently re-enabled by the next update, across every site they run. It now skips any provider with a stored preference at all (`get_option( ..., null ) !== null`), enabling only providers nobody has ever expressed an opinion about. A stored '0' is a decision; an upgrade is not a licence to overrule it.

**Fixed on operator review — one option write per rejected submission.** `record_rejection()` wrote unconditionally, so a payment form under a carding run would have turned an attack into database load: the plugin amplifying the thing it exists to absorb. Now throttled to five minutes per form per reason, matching `record_injection()`, with a change of reason always writing immediately because that is new information.

**Payment-only forms are unaffected by any of this**, which the harness confirms across Stripe, PayPal, PayPal Checkout, Square and an unrecognised gateway caught by the pricing-field fallback: `checkout` action, `checkout` context, strict, and — importantly — **no `submit` in their accepted-action list**. The compatibility allowance for cached pages deliberately stops at the money. Payment forms never had the action-pairing defect either: both sides already resolved to `checkout`, which is why this surfaced only on account forms.

**Fixed same-day — "Not public" removed protection instead of removing noise.** The first cut put `form_is_internal()` inside `form_is_eligible()`, which made the plugin wholly inert on a declared form: no token field, no scoring, no validation. On a genuinely programmatic form that is merely useless. On the account dashboard's **password-change** form — reachable in a browser, and the exact step an account takeover performs to lock the owner out — it silently removed bot scoring from a credential change. The operator caught it and was right: *"even though this is internal, it is updating a password and should be scored."*

The error was conflating two unrelated things under one switch. Whether a missing token is worth *alerting about* is a reporting preference. Whether a submission is *scored* is protection. The first must never be able to decide the second, and here a checkbox intended to quiet a false alarm was silently trading away the plugin's entire purpose on that form.

**Corrected semantics:** an internal form stays eligible and keeps its token field. The declaration suppresses exactly one thing — the missing-token alarm (coverage gap, error log, operator email). A submission carrying a token is scored regardless, so the checkbox is *inert on any form a human can reach*. Certificate still runs silently; the password form is scored again. Verified both ways in the harness.

**Added — password-changing forms are classified as such.** A `password` field means the form is a credential-changing surface, whatever mechanism applies the change. Own action (`password_reset`), own context (`gf_password`), ranked above a plain account update because it is the takeover step, not routine profile editing. Non-strict: an authenticated user must not be locked out of changing their own password over a missing token. The UI now warns when a form marked "Not public" also takes payment, changes a password or touches an account.

**Resolved, and not ours:** the password form "spinning" was Gravity Forms refusing a submission on required address fields that were empty and not visible on the page — a hidden validation failure with nothing on screen to explain it. Worth recording because the reasoning that got there was the useful part: this plugin has no branch that hangs a submission (every path either returns the result untouched or sets `is_valid = false` with a message GF renders normally), so a spinner could only come from a fatal or from GF itself. Resisting the pull to attribute it to the change that happened to land at the same time was correct.

Confirmed by inspection that we cannot mask a host-plugin validation error: `validate_submission()` returns immediately when GF has already marked the result invalid, and `validation_message()` returns the message untouched unless we ourselves rejected. So the hidden error was hidden by the form's own configuration, not obscured by us.

**Operator-supplied ground truth** (five live forms): Registration = payment + conditional create; User Profile = update (logged in); Professional Certification Exam = update, a course quiz that writes user meta (logged in); Contact and Certificate = neither. Confirmed against the harness: actions pair, contexts resolve, and only Registration is strict. Note that feed *conditional logic* is deliberately ignored — a create feed gated on "not logged in" still classifies the form as account-creating, which over-strict is the safe direction.

**Added — chunk 19 (`19-gf-action-pairing.php`)**, the regression guard: renders the real field, parses the attribute, compares it against the resolved action. Offline, no submissions, no entries — it would have caught this on any install on day one. Chunk 13 gained create-vs-update enforcement cases.

**Verified before shipping** against stub harnesses covering both files: five form classes (contact / create / update / payment / feedType-absent) all pair correctly, and eight verifier scenarios route to the right error code — including a reproduction of the original mismatch and a check that `SITE_MISMATCH` does not fail open.

**Plan:** `PLAN-gf-account-form-false-rejection.md`. It sequenced this as 2.21.2 (unblock) then 2.22.0 (classification), and that split was **not** kept: `action_for()` resolves through `form_updates_account()`, so the account-feed split is a dependency of the fix rather than a follow-on, and separating them would have meant an artificially broken intermediate. Shipped as one 2.22.0. The consequence is that staging to production is coarser than planned — the classification change cannot be held back while only the unblock goes out. If that matters, turning the GF provider off remains the zero-risk mitigation.

**Still open:** the mobile submit race — returning to a backgrounded tab and submitting before the async token refresh lands — is now *reported honestly* rather than as spam, but not eliminated. The bootstrap's submit interceptor covers only `form.login, form.register`. Extending it to GF has its own render-path risk and should wait until the new logging shows how often this actually fires.

### Phase 47 Modifications (v2.21.1)
First real use of the 2.21.0 reporting found it wrong, in the same way three earlier defects were wrong.

**Deactivating a plugin does not delete its options.** The operator restored the Gravity Forms keys, deactivated the reCAPTCHA add-on, and the Form Protection table still reported `v3 / Enterprise` on all five forms. `native_captcha_state()` read the *stored settings* and inferred a running reCAPTCHA from them. ## Historical Phase: Phase 46 (settings takeover removed; detect and warn instead)

### Phase 46 Modifications (v2.21.0)
The takeover mechanism is gone. Not narrowed, not guarded — removed.

**Why it could not be kept.** The premise was that filtering a host plugin's settings is safe because it writes nothing and reverses on the next request. That premise is false, and Phase 45 was not a bug within a sound design but the design failing exactly as it must: *any* settings screen that reads an option to populate its fields writes back what it was shown. Gravity Forms is not unusual in this; it is typical. The 2.20.5 admin-scope guard and write guard reduce the blast radius but leave a mechanism whose correctness depends on correctly enumerating every context in which a foreign plugin might read its own settings — an open-ended obligation with silent, destructive failure.

**Two further reasons, either sufficient on its own.**
- *It never demonstrated a benefit.* Phase 43 established `disable_native()` had been a no-op for several versions. Across that entire period payments worked, GF's reCAPTCHA coexisted with ours, the loader owner deduplicated the shared script, and every form received our token. The feature that destroyed a live site's configuration has not once been observed providing protection. The original Stripe outage was caused by the Conflict Guard stripping GF's loader tag and by divergent keys/script families — both fixed independently in Phases 36–44, neither dependent on takeover.
- *The bindings are unmaintainable.* One plugin, one version, three wrong guesses: the option name (Phase 43), the setting names inside it (Phase 44), the add-on class name (Phase 45, twice — unqualified `class_exists()` against a namespaced `Gravity_Forms\Gravity_Forms_RECAPTCHA\GF_RECAPTCHA`). Fluent Forms, WPForms, Formidable and PowerPack would each multiply that across versions that rename freely, with corruption as the failure mode.

**Removed:** `GSWP_Form_Provider::disable_native()` from the contract; the GF implementation, `blank_native_settings()`, `protect_native_settings()`, `is_gf_form_submission()`; and the registry call. The contract now states the prohibition explicitly — providers may read a host's configuration to report on it, never filter or write it.

**Added — `GSWP_Foreign_Recaptcha`.** Scans for site keys configured by other plugins, names each, and says whether the key matches ours, with the consequence spelled out: a different key means only one of the two can be pre-rendered and the other silently fails (the original outage); a matching key means both run, so every submission is assessed twice and the other plugin's threshold is a second invisible policy. Deliberately guess-free — it uses the same `LIKE '%recaptcha%' OR '%captcha%' OR 'gravityformsaddon%'` query that actually found the GF option in Phase 44, matches values against the Google site-key shape, and reports unrecognised findings under their raw option name rather than skipping them. Secrets are excluded (they never reach a browser, so they indicate no loader). Cached 12h, flushed on key change or plugin activation; dismissals key on a findings hash so a new or changed finding re-arms.

**Copy corrected everywhere it claimed something untrue.** The upgrade notice, the Form Protection panel, and the per-provider status all said the form plugin's reCAPTCHA "has been switched off". They now state that it keeps running until the operator turns it off, and why that matters. New guidance on the API Credentials screen: configure reCAPTCHA here and nowhere else.

**What this costs, stated honestly:** on a site whose operator ignores the notice, two reCAPTCHAs run indefinitely. That is a duplicate assessment per submission and a second threshold we cannot see. Bounded, and preferable to an unbounded risk of destroying another plugin's configuration.

**Unchanged:** everything that protects a form — token injection, markup fallback injection, the coverage assertion, asymmetric enforcement, the kill switch, transaction data on payment forms. Those are ours and touch nobody else's data. `native_captcha_state()` also stays, still reading raw via `$wpdb`, because detection is now the whole feature.

**Also:** `Diagnostics.jsx` had 35 pre-existing lint errors (33 formatting, 2 nested ternaries). Fixed — a red lint gate hides the next real `no-undef`, which is the defect it was added for in 2.20.1.

## Historical Phase: Phase 45 (this plugin corrupted Gravity Forms' settings)

### Phase 45 Modifications (v2.20.5)
The 2.20.4 binding fix worked. That is precisely why it did damage: `disable_native()` had been filtering an option that did not exist, so it had no effect anywhere. Once the names were correct, the filter started applying **on admin screens too**, and Gravity Forms' own reCAPTCHA settings page reads that option to populate its fields and writes back what it read. The operator reported the page could no longer be saved; chunk 15 then confirmed the option had been reduced to `connection_type`, `nonce` and `action` — `site_key_v3`, `secret_key_v3`, `score_threshold_v3`, `disable_badge_v3`, `recaptcha_keys_status_v3`, `site_key_v2`, `secret_key_v2` and `type_v2` all gone.

**This broke the guarantee the whole approach rests on.** The stated reason for filtering settings rather than unhooking GF's internals was that it is read-only and reversible — turn the provider off and GF's reCAPTCHA returns on the next request. A read filter that reaches a settings screen is not read-only in effect, because the screen round-trips what it reads. The mechanism was sound; the scope was not.

**Three changes, in order of importance.**
1. **Scope.** `disable_native()` now returns early on `is_admin()`. The single exception is a Gravity Forms form *submission* over admin-ajax (`is_gf_form_submission()`: `wp_doing_ajax()` plus `$_POST['gform_submit']` or an `action` beginning `gform_submit`) — GF must stay stood down there or it would validate a field it was prevented from rendering. Everything else admin-side, **including the add-on's own key-validation AJAX**, sees the real stored values. The first draft of this guard used `is_admin() && ! wp_doing_ajax()`, which would have left the validation call reading blanks and reporting the operator's freshly entered keys as invalid.
2. **A write guard, so scope alone is not the only defence.** New `protect_native_settings()` on `pre_update_option_*`, registered only where the read filter is active. On those requests no legitimate save of GF's settings exists, so a write that empties a previously non-empty key is refused and logged at error level. It is one-directional: a write that *sets* a key always passes, so it can never block an operator configuring the add-on. Scope is the fix; this is the thing that would have made the bug visible instead of destructive.
3. **Reporting no longer reads through our own filter.** `native_captcha_state()` used `get_option()`, so on the front end it read the blanked copy and concluded GF had nothing configured — which is a second, independent explanation for the perpetual `unknown` in the Form Protection table, and one that would have survived the Phase 44 name fix. ## Historical Phase: Phase 44 (GF bindings verified; cross-family dedup bug found)

### Phase 44 Modifications (v2.20.4)
Chunk 15 discovery run on staging. It fixed the binding and, more importantly, exposed a latent token-generation failure that no earlier test could have caught.

**The GF option name was right; the setting names inside it were not.**

**The serious find: dedup could silently stop token generation.**
- This site has our plugin on **Enterprise** and Gravity Forms on **classic** (`connection_type = classic`) — with the **same site key**. So GF emits `api.js?render=K` and this plugin emits `enterprise.js?render=K`.

- No test so far would have caught it: chunk 12 checks the token *field* is present, not that it is *filled*, and nothing has been exercised in a browser.
- Fixed: dedup now keys on **family + site key**. `api.js` and `enterprise.js` are different APIs that merely accept the same key, so they are never duplicates of each other. When both appear for one key, both are kept and the condition is logged at error level as an integration-type conflict — the operator should align the two plugins, but nothing breaks in the meantime.
- The option-name fix removes the collision at source on this site: once `disable_native()` actually works, GF stops emitting `api.js` at all.

**Also confirmed from the dump:** all three consumers (this plugin, GF, PowerPack `bb_powerpack_recaptcha_v3_site_key`) hold the *same* site key, so there is no divergent-key conflict on staging — the 2.18.1 warning correctly stayed silent. ## Historical Phase: Phase 28 (Password Defense — native PHP leaked-credential detection)

### Phase 28 Modifications (v2.13.0)
- **Where this came from.** The Fraud Defense console's other outstanding recommendation ("Detect
  leaked passwords — Configure Password defense") is a sibling feature to Account Defender (closed
  out in Phase 27) that the plugin did not implement at all. Google's console only offers Java/Node
  client helpers for it; PHP is "Other," pointed at the raw protocol spec
  (`docs.cloud.google.com/recaptcha/docs/check-passwords#cryptographic-function`). Full
  investigation and design in `PLAN-password-defense.md`.
- **Native PHP implementation of Google's privacy-preserving Password Check protocol** — no
  dependency on Node or an external client. Three new `includes/` classes:
  - `class-gswp-scrypt.php`: pure-PHP RFC 7914 scrypt (PBKDF2 legs via native `hash_pbkdf2()`;
    ROMix/BlockMix/Salsa20/8 in PHP). Verified byte-for-byte against both official RFC 7914 test
    vectors and the exact scrypt(N=4096,r=8,p=1) parameters the protocol uses.
  - `class-gswp-ec-cipher.php`: NIST P-256 point arithmetic (GMP preferred, BCMath fallback) —
    scalar multiplication, point compression, and the SHA-256 "random oracle" hash-to-curve
    function from Google's `private-join-and-compute` `ECCommutativeCipher`. Implemented from the
    published algorithm (not ported/translated — Apache-2.0 vs. this project's GPLv2-or-later,
    see licensing note in the class docblock) and validated against it as an external test oracle.
  - `class-gswp-password-defense.php`: orchestrator — capability gating, the standalone
    `privatePasswordLeakVerification` assessment call (no token/event required), local verdict
    computation, per-user weekly cadence, and the login/choice-time hooks.
- **Verification methodology (unusually deep for this codebase, warranted by the stakes of silent
  crypto bugs — the plan's own §4.1 warns that a wrong canonicalization or hash-to-curve step
  produces silent false negatives, not errors).** Built php8.4-gmp/bcmath from PHP's own upstream
  source (`ext/gmp`, `ext/bcmath` via `phpize`) since neither extension ships in this sandbox, then:
  1. Fetched Google's official `recaptcha-password-check-helpers` npm package (Apache-2.0) and its
     underlying `private-join-and-compute` C++ source (`ec_commutative_cipher.cc`, `ec_group.cc`,
     `context.cc`) as read-only reference/oracle — never copied into this project.
  2. Generated real test vectors by executing the official helper's WASM `EcCommutativeCipher`
     (hash-to-curve, encrypt, decrypt, reencrypt with fixed keys) and its `CryptoHelper`
     (canonicalization, username hash/prefix, scrypt pair hash) via Node.
  3. Wrote a Python prototype of the full protocol (point arithmetic, hash-to-curve, scrypt) from
     the published algorithm and confirmed it reproduces the official helper's vectors exactly.
  4. Ported to PHP (both the GMP and BCMath backends) and re-verified against the same vectors.
     This caught two real bugs before they could ship: **(a)** the hardcoded P-256 curve-order
     constant was missing a trailing hex digit, making it composite instead of prime and silently
     breaking every modular inverse (decrypt/reencrypt); **(b)** BCMath's `bcmod()` keeps the
     dividend's sign (unlike `gmp_mod()`, which always returns non-negative), so the BCMath
     backend's point arithmetic produced garbage on the first negative intermediate value until a
     manual sign-fold was added. Both backends now reproduce Google's real WASM implementation
     exactly across hash-to-curve, encrypt/decrypt, and a simulated two-party
     blind/reencrypt/strip-and-verify round trip, plus a full leak-detected / not-leaked
     end-to-end simulation.
  5. Confirmed the canonicalization quirk from the plan (Google's own helper's
     `.replace('.', '')` strips only the *first* dot despite the docs saying "stripping dots," and
     the credentials-pair scrypt hash uses the **raw**, not canonicalized, username) by reading the
     helper's `crypto_helper.ts` source directly, and matched both exactly.
- **Login path (deferred, at most weekly per user).** `authenticate` filter at priority 45 (after
  the core password check at 20 and Account Defender's capture at 40, before 2FA at 100): on a
  correct password where a per-user cadence meta (`gswp_pd_last_check`, a `{time, fp}` pair keyed
  to a `wp_hash()` of the *already-hashed* stored password so no new secret material is persisted)
  says a check is due, the credentials are stashed and checked on `shutdown` — after the response
  has been sent, so the scrypt hash and API round trip never add login latency. A detected leak
  stores `gswp_pd_leaked` meta and fires `gswp_leaked_credentials`. On a later login with the same
  (still-leaked) password, the plugin either refuses the login with a link to the lost-password
  screen (opt-in `gswp_pd_force_reset`, default off) or lets it through with a persistent
  `admin_notices` nag (default) — never a surprise lockout. The flag clears itself once the
  password's fingerprint changes (password reset, profile change, or WooCommerce account-details
  change).
- **Choice-time surfaces (inline, may block).** `validate_password_reset`,
  `user_profile_update_errors`, and `woocommerce_save_account_details_errors` each run the same
  check synchronously against the newly submitted password (these POSTs are rare, so the ~0.3–1.5s
  scrypt cost is acceptable inline) and, under `gswp_pd_block_choice` (default on), add a blocking

## Historical Phase: Phase 25 (Bind 2FA enrolment to its origin site)

### Phase 25 Modifications (v2.10.0)
- **Bug reported by the user:** on `maddogproducts.com`, a live user had 2FA enrolled via Google Authenticator. After cloning the site to `staging.maddogproducts.com`, the *same* authenticator code logged into the staging clone. The user asked whether this was expected given reCAPTCHA covering both domains, or a bug to fix.
- **Root cause (documented, not a plugin defect per se, but worth closing):** a TOTP code is `TOTP(secret, time)` — no domain binding at all. Cloning a site copies `wp_usermeta` verbatim, including `gswp_2fa_secret`, so the clone holds an identical secret and produces identical codes. reCAPTCHA is an unrelated subsystem (bot-scoring via site keys) with zero bearing on TOTP; its domain coverage neither causes nor excuses this. The real risk is cross-environment **replay** — the plugin's existing replay guard (`META_LAST_TS`) is per-database, so a code observed on a lower-trust staging box is still valid against production within its time-step. Full analysis and design written up first as `PLAN-2fa-environment-binding.md` (committed separately) before any code changed, per the user's request to review before proceeding.
- **Fix — origin-host binding.** New `GSWP_Two_Factor::META_ORIGIN` (`gswp_2fa_origin`) user meta records the normalized host (`current_site_origin()`: `home_url()`'s host, lowercased, `www.` stripped, scheme/port ignored, filterable via `gswp_2fa_site_origin` for multisite/reverse-proxy setups) a secret was enrolled on, stamped in `save_profile()` on successful enrolment and cleared in `disable_for_user()`. `secret_is_foreign()` compares it against the current site; `user_has_2fa()` — the single choke point every enforcement/challenge/profile-UI path already calls — now returns `false` whenever the secret is foreign, so a cloned code simply stops working.
- **Fail-open by design.** A foreign secret never blocks a login outright: `enforce_second_factor()` treats the user as unenrolled and falls through to password-only sign-in (or, for enforced roles, `maybe_enforce_setup()` routes them into fresh re-enrolment). This is deliberate — a legitimate production domain migration must never lock every admin out because their old secret's stamped origin no longer matches.
- **Grace-period interaction.** Grace-period state is copied by a clone too, so a stale, already-expired `META_GRACE_START` could otherwise cause an instant lockout for an enforced role the moment the foreign-secret check flips them back to "unenrolled" on the new site. New `maybe_reset_grace_for_moved_secret()` clears the grace clock once per detected origin mismatch (tracked via a new `META_GRACE_RESET_ORIGIN` meta, so a persistent site move doesn't reset the clock forever and create a permanent bypass) — called from `maybe_enforce_setup()` right before the existing grace-deadline check.
- **Grandfathering + backfill.** A secret with no recorded origin (pre-existing enrolments) is treated as not-foreign until stamped, so nothing breaks immediately on upgrade. New `gswp_backfill_2fa_origin()` in the main file, called from the existing version-gated `gswp_maybe_migrate()`, stamps the current site as the origin for every enrolled user missing one. Documented limitation: this only protects clones made *after* the upgrade — if the upgrade happens to run on an already-existing clone first, that clone stamps itself as its own origin. The reported `staging.maddogproducts.com` site needs a one-time manual fix (reset/re-enrol 2FA there) since it predates this change; called out explicitly in the new readme FAQ.
- **New setting** `gswp_2fa_env_binding` (default `'1'`, on), added to `gswp_default_options()`, `env_binding_enabled()` (mirrors `remember_enabled()`, tied to the master 2FA switch), wired through REST `get_settings`/`update_settings` (`tfa_env_binding`, boolean toggle, same pattern as `tfa_remember`), the `App.jsx` default, and a new "Disable 2FA on cloned or moved sites" toggle row in `src/components/TwoFactorNotice.jsx` (placed after the "Remember this browser" section) explaining the staging-clone scenario and that turning it off restores the old cross-copy behaviour.
- No REST route, class list, or distribution-ZIP file-list changes — all edits are inside already-shipped files.
- Docs: new readme feature bullet, a "Why did 2FA reset after I cloned my site?" FAQ (explicitly separates this from reCAPTCHA, explains the fail-open behaviour, and calls out that a database clone still copies password hashes/secrets regardless — clone hygiene is still the operator's responsibility), and a changelog entry.

## Historical Phase: Phase 21 (Application-password hardening for 2FA-enforced roles)

### Phase 21 Modifications (v2.8.0)
- Closed the last password-only authentication path for accounts our 2FA policy protects. Role-based enforcement only guaranteed a second factor on **interactive** logins; a REST API or XML-RPC login with an **application password** bypassed the challenge by design (`GSWP_Two_Factor::enforce_second_factor()` waves REST requests through, and application-password auth never reaches an interactive challenge). A new opt-in toggle disables application passwords for users in a 2FA-enforced role via the core `wp_is_application_passwords_available_for_user` filter, so a single credential can no longer authenticate an enforced `manage_options` account. Off by default (agency management tooling commonly connects via an admin application password, so on-by-default would sever those connections on a routine update).
- **Bug fixed in the same phase:** `GSWP_Two_Factor::block_non_interactive()` — the XML-RPC block for enrolled users the readme/STATE.md have advertised since v2.0.0 — **had never been hooked** (added in the rebrand commit, no `add_filter` anywhere in history). An enrolled user's real password worked over XML-RPC with no second factor. It is now wired to `authenticate` at priority 99 (after the password/reCAPTCHA/Account Defender checks at 20/30/40, just before the interactive challenge at 100), restoring the documented behaviour. It stays scoped to **enrolled** users (enforcement locks the dashboard, not authentication, so an enforced-but-unenrolled user's XML-RPC password login is no stricter than their interactive one).
- **Mechanism.** New `restrict_app_passwords( $available, $user )` on `wp_is_application_passwords_available_for_user` (priority 10) returns `! role_is_enforced( $user->ID )` when the block is on — but only ever **narrows** an already-true `$available` (returns the incoming value, never a hard `true`), so it composes with other plugins that disable application passwords. Returning `false` closes every application-password surface at once: authentication with already-issued passwords (REST **and** XML-RPC, since core's `wp_authenticate_application_password()` handles both), the profile "Application Passwords" section, the REST management endpoints, and `authorize_application.php`. Existing passwords are **rejected, not revoked** (stored meta untouched), so turning the toggle off restores them instantly with no re-issuing. Two new static predicates mirror `remember_enabled()`: `app_password_block_enabled()` (master switch + `gswp_2fa_block_app_passwords`) and `is_app_password_exempt( $user )`.
- **Scope = enforced roles, not enrolled users** (an app password minted before enrolment would otherwise be a permanent bypass; and a user who *voluntarily* enrolled in an un-enforced role never has an integration break). **No grace-period interaction** — the block applies the moment the toggle is on (grace is a dashboard-UX affordance; app passwords aren't part of 2FA setup). The 2FA master switch off unregisters both new hooks, so it doubles as a kill switch.

The exemption is surgical — it re-allows application passwords only; the account still gets the interactive 2FA challenge and every other control. Comma-separated logins, validated at save time in the REST route (`sanitize_user()` each, kept only when `get_user_by( 'login', … )` resolves, de-duplicated, re-joined) so typos are dropped rather than silently never matching; matched case-insensitively against `$user->user_login`. ## Historical Phase: Phase 20 (Admin email alerts on flagged events)

### Phase 20 Modifications (v2.7.0)
- Turned the two highest-value security signals the plugin already detects into an email to the operator, instead of a log line nobody watches: **Account Defender flagging `SUSPICIOUS_LOGIN_ACTIVITY` on an administrator-capable account**, and **Transaction Defense blocking a high-risk checkout** (both the classic checkout and the WooCommerce Checkout block). Big operational win for an agency running many sites; the hard requirement was throttling so it never becomes spam.
- **Decoupled detection from delivery via internal action hooks.** The detection sites fire plain actions — `do_action( 'gswp_suspicious_admin_login', $user, $labels, $context )` and `do_action( 'gswp_checkout_blocked', $risk, $threshold, $context )` — and the new `GSWP_Alerts` is the only shipped subscriber, keeping mail logic out of the verifier/defender classes and leaving the actions as a seam for future Slack/webhook forwarding. - New `includes/class-gswp-alerts.php` (`GSWP_Alerts`, constructed in `gswp_init()`). Two-layer **throttle pipeline** (the core of the feature): (1) per-event dedupe — a transient `gswp_alert_dedupe_{md5(key)}` keyed `login_{user_id}` (6 h window) or `checkout_{md5(billing_email ?: ip)}` (1 h window) suppresses repeats of the same event; (2) a global circuit breaker — a rolling hourly counter transient caps immediate sends at 5 (filter `gswp_alert_hourly_cap`), and anything past the cap (or anything at all in a digest mode) is appended to a queue (`gswp_alert_queue`, autoload-off, capped at 100 with a dropped-count) that the digest cron flushes as **one** summary email. Delivery mode `gswp_alert_mode` ∈ `immediate` | `hourly` | `daily`; digest modes never mail immediately and an empty period sends nothing. Emails are **sent on `shutdown`** so a slow mailer never delays the login/checkout response; `wp_mail` failures are logged under verbose logging and otherwise ignored (fail-open). Recipients come from `gswp_alert_email` (comma-separated, each `sanitize_email`/`is_email`-validated) and fall back to `admin_email`. Plain-text emails; subject/body lead with the site name since an agency watches many sites.
- **Detection wiring.** `GSWP_Account_Defender::capture_login_assessment()` now, on any `SUSPICIOUS_LOGIN_ACTIVITY` label (independent of the `gswp_ad_step_up` branch), resolves the flagged account — `$user` when the password was correct, else `get_user_by( 'login'|'email', $username )` so a wrong-password credential-stuffing attempt still resolves — and fires `gswp_suspicious_admin_login` when it passes `user_can( $target, apply_filters( 'gswp_alert_login_capability', 'manage_options' ) )`. `GSWP_Verifier::process_fraud_prevention()` (classic) and `GSWP_Blocks::validate_store_checkout()` (Store API) fire `gswp_checkout_blocked` inside their existing `risk >= threshold` block branches, alongside the existing log line, passing billing/total context (from `$_POST`+cart classically, from the `$order` in the block path). No behaviour change to either block.
- **Cron lifecycle.** `GSWP_Alerts::maybe_schedule_digest()` (on `init`, always registered) reconciles the `gswp_alerts_digest_event` schedule to the mode: scheduled at the mode's recurrence for digest modes, scheduled hourly only while an overflow queue exists in immediate mode, and cleared when the feature is off or the mode's recurrence changes. The REST route clears the event on a mode change so the next load reschedules it; a new `gswp_deactivate()` (`register_deactivation_hook`, the plugin's first) clears it on deactivation.
- Settings: new options `gswp_alerts` (default `0`), `gswp_alert_email` (`''`), `gswp_alert_mode` (`immediate`), `gswp_alert_login`/`gswp_alert_checkout` (per-event sub-toggles, default `1`), wired through `gswp_default_options()`, REST `get_settings`/`update_settings` (toggles in the `$toggles` array; `alert_email` validated+re-joined; `alert_mode` whitelisted with cron-clear on change), and the admin localizer. New React panel `src/components/AlertSettings.jsx` (master toggle, recipients input, delivery select, two event sub-toggles with the checkout one gated on `woocommerceActive`, and the standard classic-key Enterprise notice) rendered in `App.jsx` with the five defaults added.

## Historical Phase: Phase 10 (Fix 2FA popup not opening on cached AJAX-login sites)

### Phase 10 Modifications (v2.0.1)
- Fixed the 2FA code-entry popup failing to open on the live site (`maddogproducts.com`) while working on staging (`maddog.onedog.solutions`). Symptom: an enrolled user's login via the Login/Signup Popup (Xootix) AJAX form was correctly held server-side (our `WP_Error` text appeared inside the Xootix popup), but the authenticator modal never rendered (no `<div>`, no console error), locking the user out.
- Root cause: `assets/js/gswp-2fa-modal.js` only opened the modal on a full-page reload (flag cookie already present) or after catching a native `submit` event on a password form, after which it polled the flag cookie for ~10s. The live site runs **FlyingPress** (page cache + "Delay JavaScript"); with the modal script deferred until user interaction and the Xootix login submitting over AJAX, the `submit`-triggered poll never started, so the held-login flag cookie was never observed. Staging has no such optimiser, so the timing happened to work.
- Fix: replaced the `submit`-event-gated poll with a **life-of-page poll of the flag cookie** (`startPolling()`, every 500ms), plus the existing on-load check and a new `pageshow` (bfcache) check. The modal now opens the moment the server's held-login flag cookie appears — independent of which login form/plugin was used, any page cache, or deferred-script timing. `open()` is now idempotent (`isOpen` guard) so repeated polls don't re-focus or rebuild the modal.
- Bumped version to 2.0.1 (main file header, `GSWP_VERSION`, `readme.txt`, `package.json`) so the asset's `GSWP_VERSION` cache-busting query arg forces FlyingPress/CDN/browser caches to fetch the new script. The popup assets are plain files served from `assets/` (not webpack-built), so no rebuild was required.
